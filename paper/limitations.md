# Limitations

LHFM is a research prototype. The list below is deliberately long because
it is more useful to know what a model *cannot* do than to know what its
AUROC was on synthetic data.

## Data limitations

- **Synthetic only.** The entire cohort is generated by a small causal
  simulator. No participant in this dataset ever existed. The simulator's
  effect-size choices reflect plausibility, not calibration.
- **No subgroups.** The simulator does not stratify by race, ethnicity,
  socioeconomic status, geography, occupation, or device manufacturer.
- **One climate context.** Temperature follows a single sinusoidal track
  with two heat-wave events. Cold-weather effects, monsoon humidity, and
  wildfire smoke are not modelled.
- **No medications or comorbidities.** Real autonomic and sleep data is
  profoundly affected by SSRIs, beta-blockers, sleep aids, caffeine,
  alcohol, hormonal cycles, and chronic conditions, none of which are
  modelled here.
- **Single-device assumption.** Real wearable studies suffer from device
  changes mid-protocol, firmware updates, and sensor noise floors that
  shift unpredictably.

## Modelling limitations

- **Proxy targets.** "Low mood" is a single self-reported scale value
  below 4, not a depressive episode. "High stress" is a self-reported 5+
  on a 1-7 scale, not a stress disorder. "Climate vulnerability" is a
  hand-crafted rule combining heat index with HRV deviation. None of
  these are validated clinical instruments.
- **No external validation.** No held-out cohort, no different geography,
  no different season.
- **Window length.** The default 14-day window is a researcher choice, not
  the result of a length-vs-performance ablation on real data.
- **Participant embedding.** Indexed by integer ID, so the model does not
  generalize to new participants without either retraining or replacing
  the embedding with a baseline-feature lookup.
- **Causal interpretation is unsafe.** The model is correlational. Even
  with the right architecture, attributing changes in mood to specific
  sensor inputs would require interventional data.

## Engineering limitations

- **Single-machine training.** No distributed training support. CPU is
  the primary supported target; GPU works but is not extensively tested
  in this scaffold.
- **No streaming inference.** The API expects a full 14-day window per
  request. There is no incremental-update path.
- **Rule-based explanations.** The "explanation" returned by the API is
  generated by hand-written heuristics on the latest day. It is not a
  faithful interpretation of the neural network's reasoning.
- **No A/B framework.** There is no built-in scaffolding for randomized
  controlled deployment evaluation.
- **No fairness audit.** Sub-population breakdowns require additional
  metadata that the synthetic data does not carry.

## What we'd want to add before real-data use

1. Clinically validated downstream labels (PHQ-9, PSS, PSQI, etc.) with
   appropriate licensure.
2. Subgroup-stratified evaluation across at least race, ethnicity, sex,
   and a socioeconomic proxy.
3. External validation in a geographically and seasonally distinct cohort.
4. A faithful explanation method (e.g. integrated gradients) replacing the
   current rule-based panel.
5. Differential-privacy-aware aggregation paths for any cohort-level
   release.
6. A formal acceptable-use policy attached to the model weights.

The project is offered in the spirit of a public scaffold for these
extensions, not as a finished system.
